## Distributing the Custom Device

After building and validating your Express custom device, you need to package it so operators can install and use it.

---

### The finished device folder

Building the LabVIEW project produces a self-contained folder at:

```
<DeviceName> Custom Device\
  Builds\
    <DeviceName>\
      Custom Device <DeviceName>.xml
      Windows\
        <NameSpace>.<DeviceName>.dll          ← scripting API assembly
        <DeviceName> Configuration.lvlibp
        CustomDeviceInterfaces_v1.lvlibp
        Plugins\
          <NameSpace>.<DeviceName>.dll        ← scripting API (copy for System Explorer)
          <DeviceName> System Explorer.lvlibp
          <DeviceName> Deployment Hooks.lvlibp
          GUI Layout.yaml                     ← (if you added one)
      Linux_x64\                              ← (if you built for Linux RT)
        <DeviceName> Engine Linux64.lvlibp
        CustomDeviceInterfaces_v1.lvlibp
        Plugins\
```

This folder is what operators install. Everything inside it is required; do not add or remove files from the generated structure.

---

### Installing on a development or test machine

1. Copy the entire `<DeviceName>\` folder into the VeriStand **Custom Devices** directory:

   ```
   <Public Documents>\National Instruments\NI VeriStand <version>\Custom Devices\
   ```

2. Launch VeriStand and open System Explorer. The device appears in the **Add Custom Device** menu.

The path varies by VeriStand version. For example, for VeriStand 2026 on Windows:
```
C:\Users\Public\Documents\National Instruments\NI VeriStand 2026\Custom Devices\
```

---

### Packaging options

#### Option 1: Simple folder copy (recommended for internal use)

Zip the `<DeviceName>\` build output and provide it with a README that instructs operators to unzip it into the Custom Devices directory. This is the simplest approach and works well for devices used within a team or organization.

Include in the distribution package:

| Item | Contents |
|---|---|
| `<DeviceName>\` (build output) | The finished custom device; operators copy this to Custom Devices |
| Source folder *(optional)* | The LabVIEW project and XML definition, for teams that need to rebuild or modify the device |
| README | Installation steps, VeriStand version requirements, hardware dependencies, license, and contact information |

Do **not** include the `Auto Generated\APIs\Source\` C# project or the raw `Auto Generated\` tree in a distribution intended for operators — they are build artifacts, not run-time dependencies.

#### Option 2: VIPM package

Use **VI Package Manager (VIPM)** to create a `.vip` package. A VIPM package automates the file placement and can declare version dependencies.

1. Open VIPM and create a new package.
2. Set the **destination directory** to `<Common Data>\Custom Devices\<DeviceName>` using the VIPM alias `To Common Doc Dir`.
3. Add all files from the `Builds\<DeviceName>\` folder to the package payload.
4. Set version, description, and any required dependencies (VeriStand version, LabVIEW runtime, hardware drivers).
5. Build the package and distribute the `.vip` file.

Operators install the package by double-clicking the `.vip` file or by adding it through the VIPM library manager.

#### Option 3: LabVIEW installer

Use the LabVIEW **Build Installer** build specification to create a Windows installer (`.exe` or `.msi`). Set the destination for the device files to the Custom Devices directory using the installer's **destination folder** settings. This option is best for commercial devices distributed to end customers.

For instructions, see the LabVIEW Help topic [(Windows) Installer Properties](https://www.ni.com/docs/en-US/bundle/labview/page/lvdialog/installer_tab_windows.html).

### Distributing via GitHub

For open-source or community devices, hosting the distribution on GitHub is the recommended approach. The [niveristand-custom-device-wizard](https://github.com/ni/niveristand-custom-device-wizard) repository and the other NI custom device repositories provide a model to follow.

**Recommended repository structure:**

```
my-custom-device/
  README.md                   ← Installation, usage, version requirements
  CONTRIBUTING.md             ← How to contribute
  LICENSE
  Source/                     ← LabVIEW project and XML definition
  Builds/                     ← Built device folder (or generated by CI)
  azure-pipelines.yml         ← (optional) CI build pipeline
```

**Release workflow:**

1. Tag a release in Git (for example, `v1.0.0`).
2. Attach the built device folder as a `.zip` file to the GitHub Release.
3. Attach the `.vip` package (if you create one) as an additional release asset.
4. Document the minimum VeriStand version and any hardware requirements in the release notes.

Operators download the release asset, unzip it, and copy the device folder to their Custom Devices directory.

> **See also:** [Contributing to NI VeriStand custom devices on GitHub](https://github.com/ni/niveristand-custom-device-wizard/blob/main/CONTRIBUTING.md)

---

### Version compatibility

Express custom devices are tied to the VeriStand version they were built against, because the scripting API assembly references version-specific VeriStand assemblies. When you update to a new VeriStand version:

1. Update the LabVIEW project's NuGet/VIPM dependency references.
2. Regenerate the scripting API if the VeriStand API surface changed.
3. Rebuild the LabVIEW project.
4. Release a new version of the distribution package.

Document the supported VeriStand version range in your README and release notes so operators know which device version to install.
